## CI 基礎架構

三個平行 job（ruff、mypy、pytest），最後匯整到 `all-checks`。

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  ruff:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
          cache-dependency-glob: "uv.lock"
      - run: uv python install
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run ruff format --check .

  mypy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
          cache-dependency-glob: "uv.lock"
      - run: uv python install
      - run: uv sync --frozen
      - run: uv run mypy .

  pytest:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with:
          enable-cache: true
          cache-dependency-glob: "uv.lock"
      - run: uv python install
      - run: uv sync --frozen
      - run: uv run pytest --tb=short -q

  all-checks:
    runs-on: ubuntu-latest
    needs: [ruff, mypy, pytest]
    if: always()
    steps:
      - name: Check all jobs passed
        run: |
          if [[ "${{ needs.ruff.result }}" != "success" || \
                "${{ needs.mypy.result }}" != "success" || \
                "${{ needs.pytest.result }}" != "success" ]]; then
            exit 1
          fi
```

### 為什麼要有 `all-checks`？

- Branch protection rule 只需要設定**一個**必要 check，不用分別管 ruff/mypy/pytest
- 之後新增 job 只需改 `needs` 清單，不用動 GitHub 設定
- `if: always()` 確保就算前面 job 失敗，這個 job 也會執行並正確回報失敗（不然會被 skip，branch protection 會誤判為通過）

## GitHub Actions 常用參數

### `on` trigger

| 參數 | 說明 |
|------|------|
| `push` | 推送到指定分支時觸發 |
| `pull_request` | PR 開啟、同步、重開時觸發 |
| `schedule` | cron 排程 |
| `workflow_dispatch` | 手動從 UI 觸發 |
| `paths` | 只有特定路徑有改動才觸發 |

### `jobs` 層級

| 參數 | 說明 |
|------|------|
| `runs-on` | runner 環境，通常 `ubuntu-latest` |
| `needs` | 等待其他 job 完成才執行 |
| `if` | 條件執行 |
| `strategy.matrix` | 矩陣測試（多 Python 版本等） |
| `timeout-minutes` | job 超時時間 |
| `env` | 環境變數 |
| `permissions` | 明確宣告需要的權限 |

### Runner 選擇

| 情境 | 選擇 |
|------|------|
| 一般 Python 專案（預設） | `ubuntu-latest` |
| 測試 Windows 相容性 | `windows-latest` |
| 打包 macOS app | `macos-latest` |
| 多平台驗證 | `strategy.matrix` 同時跑三個 |

> ⚠️ Windows 耗費 2 倍分鐘數，macOS 耗費 10 倍，ubuntu 最省

> ⚠️ `ubuntu-latest` 目前指向 Ubuntu 24.04，如果對系統環境敏感，建議釘死版本如 `ubuntu-22.04`

## uv 相關

### Cache 設定

```yaml
- uses: astral-sh/setup-uv@v5
  with:
    enable-cache: true
    cache-dependency-glob: "uv.lock"  # lock 檔變了才 invalidate
```

`astral-sh/setup-uv@v5` 內建 cache 支援，自動 cache `~/.cache/uv`。

### `--frozen` vs `--locked`

| 參數 | 說明 |
|------|------|
| `--frozen` | 不允許修改 `uv.lock`，lock 跟 `pyproject.toml` 對不上直接報錯。**CI 推薦用這個** |
| `--locked` | 照 `uv.lock` 安裝，但語意稍微寬鬆一點 |

**CI 一律用 `--frozen`**，確保環境完全可重現。

## CD：Build & Push 到 GHCR

```yaml
# .github/workflows/cd.yml
name: CD

on:
  push:
    branches: [main]
    tags: ["v*.*.*"]
  workflow_dispatch:
    inputs:
      push_image:
        description: "Actually push to GHCR?"
        type: boolean
        default: false

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write       # 必須，否則無法 push 到 GHCR

    steps:
      - uses: actions/checkout@v4

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}   # 內建，不用手動設定

      - name: Generate tags and labels
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,prefix=sha-
            type=raw,value=latest,enable=${{ github.ref == 'refs/heads/main' }}

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'workflow_dispatch' || inputs.push_image }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

### Tag 策略

| 規則 | 觸發情境 | 產生 tag |
|------|----------|----------|
| `type=ref,event=branch` | push to main | `:main` |
| `type=semver,pattern={{version}}` | push tag `v1.2.3` | `:1.2.3` |
| `type=semver,pattern={{major}}.{{minor}}` | push tag `v1.2.3` | `:1.2` |
| `type=sha,prefix=sha-` | 任何情況 | `:sha-abc1234` |
| `type=raw,value=latest` | push to main | `:latest` |

完整 image 名稱格式：

```
ghcr.io / owner / repo-name : tag
```

### Labels

`metadata-action` 自動產生 OCI 標準 label，例如：

```
org.opencontainers.image.source=https://github.com/alice/myapp
org.opencontainers.image.revision=abc1234def
org.opencontainers.image.created=2024-01-15T10:30:00Z
```

用途：GHCR UI 顯示、`docker inspect` 追蹤來源 commit、安全掃描工具讀取。

### 版本號（Semantic Versioning）

格式：`v主版本.次版本.修訂號`

| 情境 | 範例 |
|------|------|
| 破壞性變更 | `v1.0.0` → `v2.0.0` |
| 新增功能（向下相容） | `v1.0.0` → `v1.1.0` |
| 修 bug | `v1.1.0` → `v1.1.1` |

**Push tag 的方法（兩種擇一）：**

```bash
# 方法一：git 指令
git tag v1.0.0
git push origin v1.0.0

# 方法二：GitHub UI
# repo → Releases → Create a new release → 輸入 tag → Publish
```

## 測試 Workflow 的方法

### 最推薦：`workflow_dispatch`

加在 `on:` 裡面，就可以在 GitHub Actions UI 手動觸發：

```yaml
on:
  workflow_dispatch:
    inputs:
      push_image:
        type: boolean
        default: false
```

位置：**repo → Actions → 選 workflow → Run workflow（右上角）**

優點：跑在真實 GitHub Actions 環境，`GITHUB_TOKEN` 行為與正式執行完全一致。

### 其他方法

| 方法 | 說明 | 適合情境 |
|------|------|----------|
| `push: false` | 只 build 不 push，驗證 Dockerfile 和 tag | 快速確認 build 能跑 |
| 測試 branch | 暫時在 trigger 加入 `cd-test` branch | 需要完整跑整個流程 |
| `act` | 在本機模擬 GitHub Actions | 快速本地迭代，但部分功能模擬有落差 |

## 查看 GHCR Image

**方法一：repo 首頁右側** → Packages 區塊

**方法二：直接訪問**

```
# 個人帳號
https://github.com/你的帳號?tab=packages

# org
https://github.com/orgs/org名稱/packages
```

頁面內可看到：所有 tag、push 時間、image 大小、`docker pull` 指令。

### 注意：預設是 Private

新 package 預設 private，改成 public：

```
package 頁面 → Package settings → Change visibility → Public
```

或連結到 repo（Connect repository），visibility 會繼承 repo 設定。
